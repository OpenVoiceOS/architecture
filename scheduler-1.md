# Scheduled Events Specification

**Spec ID:** OVOS-SCHEDULER-1 · **Version:** 1 · **Status:** Draft

This document defines the **scheduler**: the service that fires a
named event on the message bus at a wall-clock instant, once or on a
recurrence, on behalf of a component of a voice assistant. It defines
the schedule record, the request and response messages, how the
scheduler fires an event, what happens when an occurrence is missed,
how schedules survive a restart, how time zones and clock changes are
handled, and who may change a schedule.

This specification is **prescriptive, not descriptive**. Where an
existing implementation differs, the implementation is wrong. Mapping
to a concrete implementation lives in the appendix.

The key words MUST, MUST NOT, REQUIRED, SHOULD, SHOULD NOT, MAY, and
OPTIONAL are to be interpreted as described in RFC 2119 and RFC 8174
when, and only when, they appear in all capitals.

---

## 1. Scope

This specification defines:

- the **schedule record**: identity, owner, target event, timing,
  recurrence, payload, and policies;
- the **bus protocol**: requests, responses, the fired event, and the
  notifications the scheduler emits on its own;
- **timing semantics**: instants, time zones, recurrence evaluation,
  daylight-saving transitions, clock steps, and the misfire policy;
- **durability**: what the scheduler persists, when, and how it
  restores after a restart;
- **ownership**: which component may read or change a schedule;
- **conformance** for the scheduler and for the components that use it.

It does **not** define:

- the spoken interaction for alarms, timers, or reminders. A skill
  owns that and uses the scheduler as its clock;
- calendar semantics beyond the recurrence forms in §3.4 (no
  exceptions lists, no calendar-scoped rules);
- how a component discovers the current time zone (owned by the
  configuration model);
- the session model. A fired event replays the context of its
  request; its relation to a session is defined in §4.4 by reference
  to the session lifecycle specification.

---

## 2. Terminology

| term | meaning |
|---|---|
| **scheduler** | the single service that keeps schedules and fires their events |
| **owner** | the component (skill, plugin, service) that created a schedule, identified by its component id |
| **schedule** | one record: an owner, a target event, a timing rule, a payload, and policies |
| **occurrence** | one instant at which a schedule is due |
| **fire** | emitting the target event for one occurrence |
| **one-shot** | a schedule with exactly one occurrence |
| **recurring** | a schedule whose occurrences are generated by a recurrence rule |
| **misfire** | an occurrence whose fire happens after the due instant plus the grace period, or not at all |
| **replay** | the scheduler's evaluation of every stored schedule after it starts |
| **ephemeral** | a schedule that is never persisted and does not survive a scheduler restart |

## 3. The schedule record

### 3.1 Fields

| field | type | required | meaning |
|---|---|---|---|
| `id` | string | yes | Owner-scoped identifier, chosen by the owner. Unique within the owner. Acts as the idempotency key (§5.2). |
| `owner` | string | yes | Component id of the owner. |
| `event` | string | yes | Message type emitted on each occurrence. MUST have the form `<owner>.<name>` (§6.1). |
| `at` | instant | one of `at`, `in`, `every`, `local` | Absolute instant of a one-shot occurrence. |
| `in` | object | " | Relative delay to a one-shot occurrence (§3.4.3). |
| `every` | object | " | Fixed-period recurrence (§3.4.1). |
| `local` | object | " | Wall-clock recurrence in a time zone (§3.4.2). |
| `data` | object | no | JSON object delivered as the fired event's `data`. Default `{}`. At most 16384 bytes when serialized as compact UTF-8 JSON, measured on `data`. |
| `until` | instant | no | Recurring only. No occurrence after this instant. |
| `count` | integer ≥ 1 | no | Recurring only. Maximum number of occurrences. |
| `misfire` | string | no | `late` (default), `skip`, or `all` (§4.3). |
| `grace_s` | number ≥ 0 | no | Seconds after the due instant during which a fire still counts as on time. Default 60. |
| `ephemeral` | boolean | no | Default `false`. `true` schedules are never persisted (§5.3). |
| `context` | object | no | The context of the request that created the schedule, stored verbatim and replayed on every fire (§3.5). |

Exactly one of `at`, `in`, `every`, `local` MUST be present. A record
that has `until` or `count` together with `at` or `in` is invalid.

`count` counts occurrences as they are produced or consumed (§4.3).
It is not an index into an idealized series.

### 3.2 Instants

An **instant** is a string in RFC 3339 format with a numeric UTC
offset, for example `2031-03-29T07:30:00+01:00`. A scheduler MUST
reject an instant without an offset. The offset fixes the point on the
time line; it does not carry a time zone for recurrence evaluation
(that is what `local.zone` is for).

### 3.3 Identity

A schedule is identified by the pair (`owner`, `id`). The scheduler
MUST treat two requests with the same pair as the same schedule
(§5.2). Two owners MAY use the same `id` without conflict.

### 3.4 Recurrence

#### 3.4.1 Fixed period

```json
"every": { "seconds": 600, "start": "2031-03-29T07:30:00+01:00" }
```

| field | type | required | meaning |
|---|---|---|---|
| `seconds` | number > 0 | yes | Period between occurrences. |
| `start` | instant | no | First occurrence. Default: the instant the request is accepted plus `seconds`. |

Occurrence *n* is `start + n × seconds`. Occurrences are anchored on
the schedule, never on the previous fire time: a late fire MUST NOT
shift the following occurrences.

When a request replaces a stored schedule (§5.2), its `every.seconds`
equals the stored value, and `start` is omitted, the scheduler MUST
retain the stored `start`. An owner that re-creates the same recurring
schedule on every one of its restarts therefore keeps its phase
instead of re-anchoring on each restart.

#### 3.4.2 Wall-clock recurrence

```json
"local": { "time": "07:30", "days": ["mon", "tue", "wed", "thu", "fri"], "zone": "Europe/Lisbon" }
```

| field | type | required | meaning |
|---|---|---|---|
| `time` | string `HH:MM` or `HH:MM:SS` | yes | Local wall-clock time of each occurrence. |
| `days` | array of `mon`…`sun` | no | Days of the week on which the schedule occurs. Default: every day. |
| `zone` | string | yes | IANA time zone name in which `time` and `days` are evaluated. |

Occurrences are the instants at which the wall clock in `zone` reads
`time` on a listed day. When a daylight-saving transition makes the
wall-clock time not exist on a day, the occurrence is the first
instant after the gap; when that instant falls on a day not listed in
`days`, the occurrence is skipped. When the wall-clock time exists
twice on a day, the occurrence is the first of the two. A change of
the zone's rules changes future occurrences without any action by the
owner.

#### 3.4.3 Relative delay

```json
"in": { "seconds": 300 }
```

| field | type | required | meaning |
|---|---|---|---|
| `seconds` | number > 0 | yes | Delay from acceptance to the single occurrence. |

The occurrence is measured from the instant the request is accepted
against a monotonic reference for as long as the scheduler runs, so a
step of the wall clock does not move it and §7.1 does not apply to it.
On persistence the scheduler stores the wall-clock instant it
estimates the occurrence to fall on, and replay (§5.4) treats the
schedule as an `at` on that instant: a delay that spans a restart is
therefore only as accurate as the wall clock was when the request was
accepted.

### 3.5 Request context

The scheduler stores the `context` of the request message with the
record and replays it on every fire (§4.2). It stores what arrived: it
MUST NOT add to, remove from, or rewrite the context it was given, and
MUST take it from the request message rather than from the request
body, so a component can only schedule a fire into a context it
reached the scheduler from.

`context` is part of the record, so §5.1 persists it and replay
restores it. A schedule created by a remote participant still fires
into that participant's context after a scheduler restart.

## 4. Bus protocol

All requests are messages whose `data` is the request object. Every
request MUST receive exactly one answer, derived from the request with
the `response` derivation of the message specification, so the answer
carries the requester's session and routing keys. A response carries
`ok` (boolean) and, when `ok` is `false`, `error` (a machine-readable
code) and `reason` (a sentence for the log).

Each response's `error` MUST be one of:

| code | meaning |
|---|---|
| `invalid_record` | A required field is missing, or the timing fields contradict one another. |
| `bad_instant` | An instant carries no offset, or cannot be parsed. |
| `bad_recurrence` | A recurrence object is malformed or describes no occurrence. |
| `bad_event` | The `event` violates the namespace rule of §6.1. |
| `payload_too_large` | `data` exceeds the §3.1 cap. |
| `not_owner` | The request's `owner` does not match the authenticated identity (§6.2). |
| `internal` | The scheduler could not persist or evaluate the request through no fault of the requester. The stored state is unchanged. |

| topic | direction | purpose |
|---|---|---|
| `ovos.scheduler.schedule` | component → scheduler | Create or replace a schedule. |
| `ovos.scheduler.schedule.response` | scheduler → component | Result. |
| `ovos.scheduler.cancel` | component → scheduler | Delete a schedule. |
| `ovos.scheduler.cancel.response` | scheduler → component | Result. |
| `ovos.scheduler.get` | component → scheduler | Read one schedule. |
| `ovos.scheduler.get.response` | scheduler → component | The record plus computed state. |
| `ovos.scheduler.list` | component → scheduler | Read the caller's schedules. |
| `ovos.scheduler.list.response` | scheduler → component | Array of records plus computed state. |
| `<event>` | scheduler → bus | One occurrence fired (§4.2). |
| `ovos.scheduler.missed` | scheduler → bus | An occurrence was not fired on time (§4.3). |
| `ovos.scheduler.ready` | scheduler → bus | The scheduler has loaded its store (§5.4). |

Implementations obtain these topic strings from the platform's
message-constant registry rather than repeating the literals.

### 4.1 Requests

`ovos.scheduler.schedule` carries a complete schedule record (§3.1). The
scheduler validates it, persists it (§5.1), and only then answers.
The response carries `id`, `owner`, `next` (the next occurrence as an
instant, or `null` when there is none), and `replaced` (`true` when a
schedule with the same identity existed).

`ovos.scheduler.cancel`, `ovos.scheduler.get` carry `id` and `owner`.
`ovos.scheduler.list` carries `owner`. Cancelling a schedule that does not
exist is not an error: the response carries `ok: true` and
`existed: false`.

`ovos.scheduler.get.response` carries `ok`, `record` (the record of §3.1 as
stored), and `state`:

```json
"state": { "next": null, "last_fired": null, "missed": [], "remaining": null }
```

| state field | type | meaning |
|---|---|---|
| `next` | instant or `null` | The next occurrence, or `null` when none remains. |
| `last_fired` | instant or `null` | The due instant of the most recent occurrence fired. |
| `missed` | array of instants | The schedule's missed due instants since its most recent fire, oldest first. |
| `remaining` | integer or `null` | Occurrences left, when bounded. |

`ovos.scheduler.list.response` carries `ok` and `schedules`, an array of
the same `{record, state}` pairs. Under the pseudo-owner `*` (§6.2),
`ovos.scheduler.list` returns the pairs of every owner.

There is no update request. An owner changes a schedule by sending
`ovos.scheduler.schedule` again with the same identity and the new record;
the replacement is atomic and the previous timing is discarded.

### 4.2 The fired event

For each occurrence the scheduler emits one message of type `event`
whose `data` is the record's `data` and whose `context` is the
record's `context` (§3.5), unchanged but for one added key,
`scheduler`, describing the occurrence:

```json
"context": {
  "source": "sat-7",
  "session": { "session_id": "sat-7-kitchen" },
  "scheduler": {
    "id": "morning-brief",
    "owner": "briefing",
    "due": "2031-03-29T07:30:00+01:00",
    "fired": "2031-03-29T07:30:00+01:00",
    "remaining": null
  }
}
```

| field | type | meaning |
|---|---|---|
| `id` | string | The schedule's `id`. |
| `owner` | string | The schedule's `owner`. |
| `due` | instant | The occurrence's due instant. |
| `fired` | instant | When the scheduler emitted the message. |
| `remaining` | integer or `null` | Occurrences left after this one, when bounded. |

Everything outside the `scheduler` key came from the request. The
scheduler MUST leave every other key of the stored context exactly as
it received it, and MUST NOT drop or rewrite one.

A context carries the routing identity of the participant that asked
for the schedule — `source` and `destination` (MSG-1 §3) and the
session carrier (MSG-1 §4, SESSION-1 §3.1) — and that identity is what
a layer-2 deployment routes by. Replaying it verbatim is what makes an alarm
asked for on a remote device ring on that device rather than wherever
the scheduler happens to run. Whether a session snapshot inside the
context is still current is a consumer's question, answered under the
session lifecycle: a client owns the state of its named sessions and
resolves currency on receipt (SESSION-2 §2.5, §4.1), and the
orchestrator applies its normal derivation to whatever it dispatches.

A request that carries no context — a component scheduling for itself
on the device — produces a fire whose context is the `scheduler` key
alone, and the default session applies as it does to any message that
names none.

An owner that needs state of its own at fire time puts a key into
`data`.

The scheduler SHOULD fire within one second of the due instant. An
occurrence fired later than `due + grace_s` is a misfire even while
the scheduler is running, so `skip` suppresses it and `late` fires it
once.

### 4.3 Misfire policy

An occurrence is a misfire when the scheduler fires it later than
`due + grace_s`, or cannot fire it at all (it was due while the
scheduler was not running, or while the clock was stepped past it).
The record's `misfire` field decides what happens:

| value | behaviour |
|---|---|
| `late` | Fire the most recent missed occurrence immediately, once, with `due` set to its original due instant. Earlier missed occurrences of the same schedule are dropped. |
| `skip` | Do not fire missed occurrences. |
| `all` | Fire every missed occurrence, oldest first, each with its own `due`. |

The scheduler MAY pace `all` firings across evaluation ticks. The order stays oldest first and the bound of §4.3 still applies.

An occurrence dropped under `late` or `skip` is **consumed**: it
counts against `count` and is never retried. `all` fires missed
occurrences only up to the remaining `count`, and never past `until`.
The `remaining` of a late fire reflects the consumption of every
occurrence up to and including the one being fired.

In every case the scheduler MUST emit `ovos.scheduler.missed` once per
schedule that had at least one missed occurrence, with `id`, `owner`,
`missed` (array of due instants, oldest first), `fired_late` (the
instants that were fired under `late` or `all`), and `next`. Each of
`missed` and `fired_late` carries at most 100 entries; when either is
capped the message also carries `truncated: true`.

`next` is what distinguishes a series that lost occurrences (`next`
set) from a one-shot that will never fire (`next` null).

For one schedule, the scheduler MUST emit `ovos.scheduler.missed` before
any late fire it performs for the same evaluation.

A one-shot schedule is deleted after its occurrence is fired or
reported missed.

### 4.4 Sessions and context

A fired event is bus traffic like any other message. Consumers apply
the propagation rules of SESSION-2 to the context it replays (§4.2).
Nothing in a schedule extends the life of a session: a fire names the
session its request named, and makes no claim that the session still
exists. A consumer that no longer holds that session treats the fire
as it treats any other message naming an unknown session.

## 5. Durability

### 5.1 Write-ahead persistence

The scheduler MUST persist every accepted `ovos.scheduler.schedule` and
every `ovos.scheduler.cancel` before sending the response. It MUST persist,
for every schedule, the due instant of the most recent occurrence it
fired — after emitting the fired event, and before any further
emission or response; an occurrence at or before that instant is never
fired again. Persistence MUST be atomic at the file or transaction
level, so that a crash at any point leaves either the previous or the
new state, never a partial write.

This specification chooses at-least-once delivery bounded to a single
occurrence: a crash between emitting a fire and persisting it may
repeat that one fire on the next replay, and the never-refire bound
above keeps the window to that one occurrence. Owners MUST therefore
treat the fired event as idempotent per (`id`, `due`). A fire repeated
under this rule is also reported in `ovos.scheduler.missed`; owners
deduplicate the report by (`id`, `due`) as they deduplicate the fire.

The store lives in the assistant's **state** directory, not its
configuration directory. Its format is not part of the wire contract,
but it MUST carry the records of §3.1 unchanged so that a replacement
scheduler can read them.

### 5.2 Idempotency

A `ovos.scheduler.schedule` request whose identity matches a stored
schedule replaces it. Sending the same request twice therefore has the
effect of sending it once. Owners that re-create their schedules on
every start rely on this; the scheduler MUST NOT accumulate duplicate
records for one identity. A replacement that repeats the stored period
without a `start` keeps the stored anchor (§3.4.1), so repeated
re-creation neither duplicates the schedule nor shifts its phase.

### 5.3 Ephemeral schedules

A schedule with `ephemeral: true` is held in memory only. It is
dropped when the scheduler stops and never appears in replay. Owners
use it for schedules whose meaning dies with their own process, such
as a conversation keep-alive.

### 5.4 Replay

When the scheduler starts it MUST first load every persisted schedule
and compute its occurrences from the current time, then emit
`ovos.scheduler.ready`, and only then apply the misfire policy of §4.3 to
any occurrence that was due while it was down, emitting the late fires
and the `ovos.scheduler.missed` messages that policy calls for. Emitting
readiness before the replayed traffic gives an owner that subscribes
on `ovos.scheduler.ready` a chance to hear its own late fires.

`ovos.scheduler.ready` carries `schedules` (count restored), `missed`
(count of schedules that had missed occurrences), and `clock`
(§7.2).

A deployment MAY configure a readiness condition — a message type to
wait for, or a delay — that the emission of the replayed traffic
additionally waits on. There is no such condition by default.

Owners MUST NOT have to re-create their schedules after a scheduler
restart, and MUST NOT assume the scheduler is empty when they start.

An owner reconciles its state by listing its schedules after it
starts. Every schedule under an owner belongs to that owner alone, so
an id the owner no longer recognizes is stale and safe to cancel;
owners keep the ids of long-lived housekeeping schedules stable so
reconciliation can tell them apart.

## 6. Ownership

### 6.1 Namespacing

The `event` of a schedule MUST have the form `<owner>.<name>`: the
owner's component id, a dot, and a name the owner chooses. The
`<name>` part MUST NOT be empty and MUST NOT contain `:`. The
scheduler MUST reject a schedule whose `event` is outside the owner's
namespace with `bad_event`.

A fired event is therefore always attributable to its owner, and can
never impersonate a message type owned by another component or by the
platform. The dot form is also deliberately unable to collide with
the single colon-bearing dispatch shape of the message specification
(§2.1.1): a schedule cannot be used to address another component's
registered handler.

### 6.2 Authority

`ovos.scheduler.schedule`, `ovos.scheduler.cancel`, `ovos.scheduler.get`, and
`ovos.scheduler.list` act only on schedules whose `owner` equals the
request's `owner`. Where the bus carries an authenticated component
identity, the scheduler MUST refuse a request whose `owner` differs
from that identity with the error `not_owner`. Where the bus does not
authenticate, the scheduler MUST still scope every one of those
operations to the `owner` field, so that a component cannot reach or
create under another component's identity by omission.

A privileged administrative component MAY be granted the pseudo-owner
`*` for `ovos.scheduler.list` and `ovos.scheduler.cancel`. How that grant is
made is a deployment matter and is out of scope.

### 6.3 Owner lifecycle

Schedules outlive their owner's process by default. An owner that
stops and does not want its schedules to fire in its absence cancels
them or marks them `ephemeral`. A fired event with no listener is not
an error for the scheduler; it remains visible through the `missed`
and `last_fired` state of §4.1, so an owner that starts after its own
fire reconciles by reading or listing its schedules.

## 7. Time

### 7.1 Clock

The scheduler evaluates due-ness against the wall clock, because
schedules are expressed in wall-clock instants. It MUST detect steps
of the wall clock (a change that is not the passage of time) by
comparing against a monotonic clock, and on a step it MUST
re-evaluate every schedule: occurrences that were skipped over are
misfires (§4.3); occurrences that moved into the future are simply
waited for. The persisted most-recent-fire instant of §5.1 bounds
this: an occurrence at or before it is never fired again, so a step
cannot walk a schedule back over occurrences it has already fired.

### 7.2 Unsynchronized clock

A scheduler on a device without a battery-backed clock may start
before the clock is set. The clock is **unsynchronized** when the wall
clock reads earlier than the newest instant the scheduler has
persisted **as already past** — the due instant of the most recent
fire it recorded, or the wall-clock time of its most recent store
write, whichever is later. The scheduler MUST record the wall-clock
time of every store write for this purpose. It becomes **synchronized**
when the wall clock passes that instant, or when a synchronization
signal defined by the deployment arrives. A first boot with an empty
store has no such instant and is therefore synchronized by
definition; a deployment on hardware without a battery-backed clock
SHOULD provide the synchronization signal so that first boot is still
covered.

While the clock is unsynchronized the scheduler MUST accept requests,
persist them, and defer evaluation; it MUST NOT drop or refuse them.
`ovos.scheduler.ready` carries `clock`, which is `"synchronized"` or
`"unsynchronized"`. On the transition to synchronized the scheduler
performs the replay of §5.4, including the emission of a second
`ovos.scheduler.ready`.

### 7.3 Time zones

Instants carry their own offset (§3.2). Only `local` recurrences
carry a zone, and it is the zone the owner chose, which need not be
the device's zone. A change of the device's configured zone changes
nothing in existing schedules; an owner that wants "07:30 wherever
the device is" re-creates the schedule when the zone changes.

## 8. Client library

A component-facing library that wraps this protocol MUST:

- send and await the response of every request, and surface an
  `ok: false` response to the caller as an error;
- accept a time-zone-aware datetime for `at` and reject a naive one,
  or convert it using an explicitly configured zone, never the
  process's local zone by accident;
- register the owner's handler for `event` before sending
  `ovos.scheduler.schedule`, so that an occurrence due immediately is not
  lost;
- expose `list` so that a component can enumerate its own schedules
  and reconcile them with its own state.

A library does nothing to make a schedule fire back at the participant
that created it: the scheduler stores the request's context and
replays it (§3.5). A library MUST NOT put routing keys or a session
into the request body to that end.

It SHOULD derive a default `id` from stable names the caller supplies,
never from the identity of the handler function, and MUST document
that an omitted `id` together with a renamed handler can orphan the
old schedule.

The library owns the handler it registers: `cancel` MUST remove the
handler the corresponding `schedule` registered, and replacing a
schedule MUST NOT leave a second handler behind.

A library SHOULD give each schedule its own event name; owners that
route several schedules through one event name distinguish occurrences
by the `scheduler.id` context field.

## 9. Conformance

### A **scheduler** MUST:

1. Validate every field of §3.1 and answer every request exactly once,
   with the `response` derivation and one of the §4 error codes (§4).
2. Persist before answering, and persist the most recent fired
   occurrence after emitting it and before any further emission or
   response (§5.1), atomically.
3. Replace on identical identity, never duplicate, and keep the stored
   anchor of an unchanged period (§3.4.1, §5.2).
4. Restore all non-ephemeral schedules on start, emit
   `ovos.scheduler.ready` with `schedules`, `missed` and `clock`, and only
   then apply the misfire policy and emit the replayed traffic (§5.4).
5. Store the request's context verbatim, persist it with the record so
   it survives a restart, and fire with that context plus the added
   `scheduler` object and no other change (§3.5, §4.2, §5.1).
6. Emit `ovos.scheduler.missed` for every schedule with missed occurrences,
   respecting the consumption rules and the 100-entry caps (§4.3).
7. Anchor fixed-period recurrences on the schedule, measure `in`
   against a monotonic reference (§3.4.3), and evaluate wall-clock
   recurrences in their zone with the daylight-saving rules of §3.4.2.
8. Enforce the `<owner>.<name>` shape of `event` and scope every
   request, including `ovos.scheduler.schedule`, to its `owner` (§6).
9. Never fire an occurrence at or before the persisted most recent
   fire (§7.1); defer, not drop, while the clock is unsynchronized,
   and replay on the transition to synchronized (§7.2).

### An **owner** MUST:

1. Use a stable `id` for a schedule it re-creates across its own
   restarts, and rely on replacement rather than cancel-and-create.
2. Register its handler for `event` before scheduling.
3. Treat the fired event as idempotent per (`id`, `due`) (§5.1).
4. Treat `ovos.scheduler.missed` as the signal that an occurrence did not
   happen on time, and decide what to tell the user.
5. Put any state it needs at fire time into `data` rather than in the
   request context, which is replayed as it was and does not track
   the world since.
6. Mark process-bound schedules `ephemeral`.

### Non-goals

- A general job queue or retry engine.
- Sub-second timing guarantees.
- Distributed scheduling across several assistants.
